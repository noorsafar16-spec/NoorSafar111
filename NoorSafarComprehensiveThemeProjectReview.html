NoorSafar — Comprehensive Theme & Project Review

Design Reconstruction • WordPress Architecture • Consolidation • QA • Final ZIP Plan

Review basis: noorsafar-theme.zip + New folder.zip, including the visual reference, theme source, Core plugin, QA records, build artifacts, demo assets and supporting documentation.

Review date: 1 October 2026

1. Executive Summary

The two supplied packages contain substantial NoorSafar work, but they represent two related layers of the project rather than one already-certified production package. The first ZIP is primarily the visual/theme implementation. The second ZIP is the broader project workspace containing that theme lineage, a separate technical v2 theme, the NoorSafar Core plugin, source imagery, QA/build documentation and candidate ZIPs.

The supplied Web Demo/reference is a strong visual master: deep emerald/teal, warm ivory, antique gold, cinematic Islamic-travel imagery, editorial typography, rounded cards, mihrab/arch motifs and restrained 2D/3D motion. The current visual theme already implements the requested homepage section order as component files. The technical v2 work contains valuable booking, CPT, prayer-time, AJAX, security and RTL foundations.

The correct finalization strategy is therefore consolidation—not another unrelated rebuild: retain the approved visual theme as the presentation master, retain the hardened Core plugin as the business-logic layer, remove duplicate/legacy implementations, wire every visual component to the plugin's dynamic data model, then run full WordPress staging QA. The packages must not be described as production-certified until runtime QA passes.

5. Homepage Implementation Blueprint

Hero data

Hero image, eyebrow, title, subtitle, badge text and CTA URLs must be editable. The final approved hero artwork should be used rather than a development placeholder.

Packages

Query published package CPT records. Price is manually entered by the administrator. Status controls whether a numeric price or text such as Coming Soon / Price Not Set / Contact for Price / Sold Out is displayed.

Destinations

Use destination records or controlled options. Each card needs title, image, URL and optional accent treatment.

Trust section

Benefits and imagery should be editable, but the six benefit positions should remain visually stable to preserve the reference composition.

Audio

Use an Audio Track CPT with title, category, thumbnail and file. If no rights-cleared audio exists, hide the section rather than shipping fake tracks.

Gallery

Use Gallery/media records with thumbnail, high-resolution image and caption. Do not market AI-generated demo images as real trip moments.

Testimonials

Use only real, consented testimonial CPT records in production. No fallback demo identities should be visible after launch.

CTA/Footer

All contact, WhatsApp, social and legal links should come from one settings source.

8. Pricing and Currency Rules

Prices must remain manually controlled. The admin workflow should be: Market Assessment → Government Requirements → Taxes/Charges → Business Pricing Decision → Final Published Price → Publish. The site must never auto-calculate a selling price from market data.

9. Technical Consolidation Plan

  1. Use the visual theme as the single presentation baseline: header, footer, front page and template-parts/home/*.
  2. Use the hardened NoorSafar Core plugin as the single business-logic layer for CPTs, booking, settings, prayer times, AJAX, security and admin data.
  3. Do not ship both the old technical v2 theme and the visual theme.
  4. Remove or neutralize duplicate CPT/business-logic registration in the theme where Core already owns the feature.
  5. Keep theme-side wrappers only where they adapt presentation to Core APIs/shortcodes.
  6. Add/verify dedicated frontend templates for every public CPT actually used by the navigation.
  7. Move contact/social/business values fully into NoorSafar → Settings; eliminate hardcoded duplicates from header/footer/schema.
  8. Replace placeholder/demonstration media with approved production media or clearly mark content as staging.
  9. Wire language switching to a real multilingual plugin or a documented single-language/RTL strategy.
  10. Build the final packages from one master workspace only.

10. Findings From the Supplied Source

Area

Finding

Visual implementation

The visual theme already has componentized homepage files and the correct reference order. This is the right base for visual fidelity.

Technical foundation

The broader project contains a Core plugin with booking, CPTs, Islamic tools, admin classes, AJAX and security layers.

Runtime certification

The supplied QA records explicitly state that static checks passed but runtime WordPress QA was not performed on the development machine.

Duplicate architecture

The workspace contains a visual theme branch and a separate technical v2 theme branch. These should be treated as reference layers, not two production themes.

Hardcoded contact values

The visual theme still contains display contact values in header/footer/schema even though comments describe Core settings as the source of truth. These should be removed from templates.

Navigation defects

The header currently contains the visible spelling “Ziyaret” in one navigation item and its Book My Journey CTA points to a homepage anchor. The final route should be the dedicated booking page.

Language switch

The header contains conditional language-switch logic tied to WPML-style functions; a complete multilingual implementation still needs a verified plugin/configuration and real translations.

Audio

The audio template references placeholder upload paths. Rights-cleared audio must be supplied and tested or the section should be hidden.

Testimonials

The theme includes demo fallback testimonials. Production must use real, consented testimonial records.

Gallery

The visual theme includes AI/generated hero imagery and mockup thumbnails. These are suitable for design demonstration but should not be represented as real trip photography.

Legal

Privacy, terms and cancellation content require owner/legal review before launch.

Several reference assets are intentionally small mockup crops. Production imagery should be replaced by properly sized WebP/AVIF/JPEG assets.

360 viewer

The technical documentation correctly notes that a real 360 viewer needs a sequential frame set; a handful of gallery images is not a true 360 sequence.

12. Staging QA Gate — Required Before Production

  1. Fresh WordPress staging installation with PHP 8.x and MySQL/MariaDB.
  2. Activate NoorSafar Core first, then NoorSafar theme.
  3. Permalinks: Post name; save/flush rewrites.
  4. Verify all CPTs, taxonomies, admin meta boxes and settings.
  5. Verify homepage at 390, 768, 1024 and 1440 widths.
  6. Verify RTL at mobile and desktop widths.
  7. Verify no PHP warnings/notices/fatal errors with WP_DEBUG enabled.
  8. Verify browser console and network requests are clean.
  9. Submit booking: database record → admin notification → customer email → WhatsApp link.
  10. Test seat inventory and all booking status transitions.
  11. Test prayer times, API fallback and cached response.
  12. Test Qibla/tasbih/Hijri where enabled.
  13. Test audio play/pause/seek/category switching with real files.
  14. Test carousel, lightbox, search overlay and video modal with keyboard, Esc and focus return.
  15. Test language switch with real Urdu/Arabic content.
  16. Test image lazy loading, WebP/AVIF/JPEG fallback and hero priority.
  17. Run SEO/schema, sitemap, canonical, Open Graph and multilingual/hreflang checks.
  18. Run accessibility checks including focus, contrast, alt text and reduced motion.
  19. Run security scan, backup/restore test and SMTP delivery test.
  20. Only after all gates pass should the final ZIPs be promoted to FINAL-UPLOAD.

14. Final Build Sequence

  1. Freeze the supplied reference image and brand tokens as the visual master.
  2. Consolidate the visual theme + hardened Core plugin into one master workspace.
  3. Resolve duplicate CPTs, duplicate settings and duplicate business logic.
  4. Finish all missing/dedicated templates and data bindings.
  5. Clean navigation, contact values, language switch, demo fallbacks and asset paths.
  6. Replace/optimize production imagery and audio.
  7. Build clean noorsafar-theme.zip and noorsafar-core.zip.
  8. Install on a clean staging WordPress site.
  9. Execute the complete runtime QA gate.
  10. Fix every failed test and rebuild.
  11. Repeat staging QA until the full gate passes.
  12. Promote only the verified packages to FINAL-UPLOAD.
  13. Perform a final production smoke test after deployment.

15. Final Assessment

The supplied materials are sufficient to continue toward a complete NoorSafar WordPress build. The visual theme should be treated as the design master, while the NoorSafar Core plugin and its corrected technical components should supply the business logic. The project is not yet a production-certified final ZIP because runtime WordPress QA, real content, SMTP delivery, multilingual verification, asset replacement and several integration clean-ups remain.

The most important architectural rule for the final package is separation of responsibility: Theme = appearance/templates/UI; Core Plugin = data/business logic/security/booking/tools. This keeps the design editable and maintainable while allowing the visual layout to remain faithful to the supplied reference.
